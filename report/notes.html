00封面30 秒

大家好，我是資管四技二乙的朱嘉瑋。我的 Redis 專題叫騎跡 RideTrace，是給機車車隊用的即時定位系統。口號是「整隊一起出發，一個都不少」。

背景這張會動的地圖就是系統的登入頁

01動機與目標50 秒

我常跟朋友騎山路，最常發生四件事：有人落隊沒人發現、在岔路走散、到集合點不知道誰還沒到、回家想看整趟只有各自零散的紀錄。

所以騎跡要做四件事：即時看到全隊、自動警示、整趟回放、長期紀錄。

因為這是資料庫課，接下來每一章我都從一個功能出發，講背後的資料怎麼存、怎麼查、為什麼用 Redis、換成 SQL 會怎樣。

02為什麼是 Redis60 秒

選資料庫之前先看資料長什麼樣。騎跡的資料是寫多讀少：每個人每兩三秒一筆；要即時推送；要地理查詢和時間序列；很多資料會過期，像心跳、邀請碼。

這些關聯式資料庫都做得到，但要加 PostGIS、TimescaleDB、訊息佇列、快取、排程器。Redis 8 一個服務就涵蓋，而且在記憶體裡跑，一個指令是微秒等級。

03系統架構50 秒

架構很簡單：手機回報位置給 FastAPI，API 寫進 Redis，同時用 Pub/Sub 推給全隊；需要判斷的事，例如落隊，交給 Worker 從 Stream 領取。路線用本機的 Valhalla 算，位置不送到 Google。

部署是推上 GitHub 就自動上線：CI 跑冒煙測試，通過後我家的 Windows 電腦自動部署，用 Tailscale Funnel 公開。

04資料模型90 秒

Redis 沒有資料表、JOIN、外鍵，所以做法跟 SQL 相反：先想好要怎麼查，再決定存成什麼型別。

點 ER 圖的「行程」→「即時狀態」→「足跡」

例如行程本身是一個 Hash；成員是多對多，就用兩個方向各一個集合；即時位置要查距離，所以放 GEO；軌跡要依時間讀，所以放 Stream。

關聯式的主鍵用 INCR、UNIQUE 用 SET NX、外鍵就是把 id 放進 key 名稱裡。

05開團50 秒

右邊是首頁，有進行中的行程

開團時 INCR 拿流水號；邀請碼用 SET NX EX，撞號就換一組，24 小時後自己消失，不用排程刪。

開始行程要防止兩個人同時按，用 WATCH 做樂觀鎖，被搶先就重試。

點「換成 SQL」：SQL 要 FOR UPDATE 鎖住那一列，還要排程刪過期邀請碼

06一筆 GPS 回報70 秒

按「播放」

這是整個系統最關鍵的路徑。一筆位置進來，API 用 Pipeline 把 15 個指令一次送出：寫足跡、寫軌跡、更新 GEO、寫速度海拔的 TimeSeries、PUBLISH 給全隊、重設心跳，最後 XADD 交給 Worker。

注意這裡刻意不包交易：Pipeline 只是減少網路來回。這些寫入彼此獨立，包交易反而拖慢高頻寫入。真正需要原子性的判斷交給 Worker 的 Lua。

07即時地圖60 秒

右邊是行程頁，五個人沿中橫在騎（3/14 真實紀錄，30 倍速）

每個人的位置放在同一個 GEO 集合，GEOSEARCH 就能算隊友距離。畫面不靠輪詢：Redis PUBLISH，所有連著的瀏覽器就收到。

如果用 SQL，前端要每兩秒輪詢一次，十個人就是每秒五次查詢；Pub/Sub 只在有新位置時送，延遲是毫秒。

08警示80 秒

警示用 Streams 加 Consumer Group：兩個 group 各拿一份完整訊息，同一個 group 開多個 Worker 就自動分攤。處理完才 XACK，Worker 當掉的話別人用 XAUTOCLAIM 接手。

代價是同一筆可能處理兩次，所以每個判斷都要冪等。「全員到齊」寫在一段 Lua 裡：SADD、SDIFF 算誰沒到、SET NX，兩個 Worker 同時判斷也只會通知一次。

落隊用「沿路線里程」判斷：山路髮夾彎直線只差 400 公尺，沿路線可能已經落後 3 公里。

右邊行程頁切到「訊息」，看事件

09失聯50 秒

失聯是「沒有發生的事」，要怎麼偵測？讓 key 自己過期。每筆回報重設心跳 SET EX 90，90 秒沒回報 key 就過期，Redis 發出 Keyspace Notification，API 收到就發警示。

SQL 要排程一直掃全表，掃的頻率決定延遲；Redis 是事件驅動，沒人失聯時完全不花資源。

10規劃路線60 秒

右邊是規劃頁：埔里到太魯閣

15.6 萬筆地名和 POI 用 RediSearch 建中文全文加地理索引，打字就自動完成。一個查詢可以同時用全文、標籤、數值、地理四種條件。

路線有幾千個座標，存成 RedisJSON，JSON.GET 只取摘要。估時用 TS.MRANGE GROUPBY 算我自己在各種路的平均速度。

11回放60 秒

右邊回放頁按 ▶，拖時間軸，點一個事件跳過去

軌跡、事件、聊天都是 Stream，ID 就是毫秒時間戳，XRANGE 依時間取就好，不用另外建索引。速度海拔是 TimeSeries，一個 TS.MRANGE 取全隊，順便每 30 秒平均一點。

12足跡與鄉鎮70 秒

右邊是我一整年的足跡：點亮 298 個鄉鎮

這是我一年 358 天、16.5 萬個點的真實資料。地圖切成 160 公尺的格子：去過的格子放 Set，選日期就 SUNION；熱力圖是 Sorted Set 計數；格子在哪個鄉鎮用 GEOSHAPE 多邊形索引查。

SADD 的回傳值直接回答「是不是第一次點亮」，不用先查再寫。

切到「熱力圖」

13匯入舊紀錄70 秒

右邊統計分頁最下面，選一個檔案，看進度條

可以匯入靈感足跡的 GPX、Google 地圖時間軸。問題是 Stream 的 ID 必須遞增，比最後一筆舊的點加不進去。

所以 Worker 把舊足跡和新的點合併，在暫存 key 整份重建，最後用 WATCH、MULTI、一連串 RENAME 一次換上。期間有新的 GPS 點寫進來，WATCH 會讓交易失敗、重新合併，騎車中匯入也不會掉點。30 萬點大約 9 秒。

14交易與一致性60 秒

用 ACID 檢查 Redis：原子性有 MULTI/EXEC 和 Lua，但沒有 rollback；一致性要程式自己保證；隔離性因為單執行緒，天生可序列化；持久性看設定，AOF 每秒寫一次，最多掉一秒。

Worker 是 at-least-once，所以里程依時間戳去重、推播用 SET NX 去重。

15持久化與資料量45 秒

記憶體資料庫關機不能掉資料：AOF 類似交易日誌，RDB 是快照；noeviction 讓記憶體滿了寧可報錯也不偷刪資料。

心跳、登入、快取都用 TTL 自己清。目前大約 17 萬個 key、384 MB。

16Redis 不擅長的地方45 秒

Redis 也有不適合的地方：臨時報表沒有 JOIN、GROUP BY；資料大了記憶體很貴；約束要自己寫。實務上會兩個一起用：Redis 處理即時，結束的行程歸檔到 SQL 做分析。

17戰情室與後台45 秒

右邊是戰情室（大螢幕版）

戰情室給在家或支援車上的人看，跟行程頁訂閱同一個 Pub/Sub 頻道。沿途天氣和路況呼叫外部 API，用 cache-aside 加 SET NX 鎖，只讓一個 Worker 去抓，避免額度被用完。

（可選）右上切「正式機即時」，看家裡電腦上真的在跑的 Demo 車隊

18開發過程與 AI 協作80 秒

這個專題 8 天、284 個 commit，程式主要由 Claude Code 寫。我負責決定功能、驗收、實際騎車測試。每次結束都寫交接紀錄，下次從那裡接。

品質靠 CI 冒煙測試、無頭瀏覽器截圖、兩輪 UI/UX 實測。AI 也犯過錯，例如匯入工具直接 XADD，舊的點被 Redis 拒絕但錯誤被吞掉，看起來像成功；還有把含家裡座標的 log 寫進 repo，公開前才掃出來清掉。

19成果、心得60 秒

最後用了 15 種以上的 Redis 進階功能。心得有三點：資料模型比程式重要，型別選對程式就短；原子性要放進資料庫，寫在 Python 一定有競爭條件；跟 AI 合作一定要有驗收機制。

還沒解決的是手機網頁鎖螢幕就不能定位，之後會包成 App。
