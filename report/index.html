    01 · 動機與目標

    跟朋友騎山路，最常發生四件事

    有人落隊沒人發現、在岔路走散、到了集合點不知道誰還沒到、回家想看整趟只有各自零散的紀錄。

    1

    即時看到全隊

    每個人每 2～3 秒回報位置，全隊地圖同步更新

    2

    自動警示

    落隊、失聯、偏離路線、異常久停、SOS，系統主動通知

    3

    整趟回放

    全隊同步播放，事件時間軸、速度與海拔曲線

    4

    長期紀錄

    全年足跡、點亮全台 368 個鄉鎮、熱力圖

    刻意不做速度排行榜，避免鼓勵飆車。所有位置資料只存在自己的伺服器，路線計算用本機的 Valhalla，不送到 Google 或公開的路線服務。

    這是一門資料庫課。以下每一章都從一個功能出發，講它背後的資料怎麼存、怎麼查、為什麼選 Redis，以及換成 SQL 會遇到什麼。

    02 · 工作負載分析

    先看資料長什麼樣，再選資料庫

    騎跡的資料是寫多讀少、要即時推送、要地理和時間查詢、很多會過期。這幾點剛好都是 Redis 的強項。

    特性騎跡的情況SQL 要補什麼
    寫入多每位騎士每 2～3 秒一筆，一筆要更新十幾個地方單筆寫入要夠快、要減少網路來回
    即時推送位置 1 秒內出現在全隊畫面資料庫不會「推」，要輪詢或另外架訊息服務
    地理查詢隊友距離、前方 1 km 的測速照相、這個點在哪個鄉鎮PostGIS
    時間序列回放的速度、海拔曲線，要依時間取、要降採樣TimescaleDB 或自己寫
    會過期心跳、登入、邀請碼、快取排程定期 DELETE
    背景工作落隊、統計、推播交給 Worker，當掉不能掉資料RabbitMQ／Kafka
    Redis 8 一個服務＝ PostgreSQL＋ PostGIS＋ TimescaleDB＋ RabbitMQ＋ 快取＋ 排程器

    Redis 8 內建 Search、JSON、TimeSeries 模組，全部在記憶體中執行，單一指令是微秒等級。代價是記憶體比硬碟貴、沒有 JOIN（第 16 章會講）。

    03 · 系統架構與部署

    一個 API、一個 Worker、一個 Redis

    手機回報位置給 FastAPI，API 寫進 Redis 並透過 Pub/Sub 推給全隊；需要判斷的事交給 Worker 從 Stream 領取。

    部署：推上 GitHub 就自動上線

    Mac 開發 → 推到 GitHub → GitHub Actions 跑 CI（語法檢查＋冒煙測試，包含註冊、開團、回報、匯入）→ 通過後 Windows 正式機每分鐘檢查一次、自動部署 → Tailscale Funnel 把 https://node.tail866fc3.ts.net:8443 公開到網際網路。

    這份報告網頁本身放在 GitHub Pages，右邊的操作展示是同一份前端程式，只是把 API 換成錄好的資料，所以正式機關機時也能看。

    04 · 資料模型

    先畫 ER 圖，再依「怎麼查」決定怎麼存

    Redis 沒有資料表、沒有 JOIN、沒有外鍵。做法跟 SQL 相反：先想好要怎麼查，再決定資料放成什麼型別。點下面的實體，看它在 Redis 裡變成哪些 key。

    04 · 資料模型（續）

    關聯式的概念怎麼搬進 Redis

    沒有 schema 的資料庫，規則要自己訂。下面是騎跡用的對應方式。

    關聯式騎跡的做法例子
    一列資料一個 Hashuser:{uid}、trip:{tid}
    主鍵 AUTO_INCREMENTINCR 計數器INCR seq:trip
    UNIQUESET … NX 搶占SET username:wei 1 NX
    外鍵id 放進 key 名稱trip:57:state:24
    多對多關聯表兩個方向各一個集合trip:{tid}:members、user:{uid}:trips
    彙總表寫入時就算好（反正規化）trip:{tid}:stats:{uid}
    二級索引RediSearch FT.CREATEidx:poi、idx:speedcam

    所有 key 的命名集中寫在 backend/app/db.py 的 class K，格式是「實體:id:子資料」，等於這個資料庫的 schema 文件。

    05 · 開團

    主鍵、唯一鍵、會過期的邀請碼

    建立行程拿到流水號，產生 6 碼邀請碼，24 小時後自動失效；開始行程時要防止兩個人同時按。

    trips.py
    # 主鍵：原子遞增
INCR seq:trip                          → 57
HSET trip:57 name "中橫" owner 1 status planned
# 邀請碼：搶不到（撞號）就換一組；24 小時自動消失
SET invite:QF963Z 57 NX EX 86400
SADD trip:57:members 1
# 開始行程：樂觀鎖，有人搶先改了就重試
WATCH trip:57 trip:57:members
HGET  trip:57 status                     → planned
MULTI
  HSET trip:57 status live started 1795423845037
  SADD trip:57:active 1 24 25 26 27
EXEC                                     → nil 代表被搶先，重來
    INSERT INTO trips(name, owner, status) VALUES ('中橫', 1, 'planned');  -- AUTO_INCREMENT
INSERT INTO invites(code, trip_id, expires_at)
  VALUES ('QF963Z', 57, NOW() + INTERVAL 1 DAY);   -- UNIQUE(code)，撞號會丟錯
-- 過期要靠排程：DELETE FROM invites WHERE expires_at < NOW();
BEGIN;
SELECT status FROM trips WHERE id = 57 FOR UPDATE; -- 悲觀鎖
UPDATE trips SET status = 'live', started = NOW() WHERE id = 57;
INSERT INTO trip_active SELECT trip_id, user_id FROM members WHERE trip_id = 57;
COMMIT;
    Redis 的 TTL 讓邀請碼自己消失，不用排程；WATCH 是樂觀鎖，不會把整列鎖住。

    06 · 寫入路徑

    一筆 GPS 回報，一次網路來回寫完十幾個地方

    回報一進來，API 用 Pipeline 把所有指令一次送出，再用 Pub/Sub 推給全隊、用 Stream 交給 Worker。按「播放」一步一步看。

    { lat: 24.1838, lon: 121.2826, speed: 11.2, ts: … }
    手機POST /api/track
    Pub/Subtrip:57:live → WebSocket → 全隊畫面
    Worker：stats里程（Lua 去重）、熱力圖、點亮鄉鎮
    Worker：alerts落隊、抵達、測速、偏離、久停
    為什麼不包成交易？這裡用的是 pipeline(transaction=False)：只是減少網路來回，不保證原子性。位置、軌跡、速度彼此獨立，一個失敗不該拖累其他的，而且交易會讓高頻寫入變慢。真正需要原子性的判斷（落隊、全員到齊）交給 Worker 的 Lua。

    07 · 騎乘中

    GEO 存位置、Pub/Sub 推給全隊

    每個人的最新位置放在同一個 GEO 集合，要算隊友距離、找最近的人直接查；畫面更新不靠輪詢，Redis 一 PUBLISH，所有連線中的瀏覽器就收到。

    ingest.py、live.py
    GEOADD trip:57:geo 121.2826 24.1838 24
GEOSEARCH trip:57:geo FROMMEMBER 24 BYRADIUS 50 km ASC WITHDIST
→ 24 0 km、25 0.42 km、1 1.8 km …
PUBLISH trip:57:live '{"kind":"pos","uid":24,"lat":24.1838,…}'
# API 每個 WebSocket 連線 SUBSCRIBE trip:57:live，收到就轉給瀏覽器
    -- 要 PostGIS
SELECT uid, ST_Distance(pos::geography, me::geography)
FROM rider_state WHERE trip_id = 57 ORDER BY 2;
-- 資料庫不會主動通知：前端每 2 秒輪詢一次
SELECT * FROM rider_state WHERE trip_id = 57 AND updated_at > :last;
-- （PostgreSQL 的 LISTEN/NOTIFY 可以，但 payload 上限 8 KB、沒有持久化）
    10 個人同時騎，輪詢要每人每 2 秒查一次；Pub/Sub 只有「有新位置」時才送，而且延遲在毫秒等級。

    行程開始前的位置也會更新 GEO 並廣播（集合時看得到彼此），但不寫軌跡、不算統計，按下開始那一刻才開始記錄。

    08 · 警示

    Streams＋Consumer Group：可靠的背景工作

    每筆回報 XADD stream:ingest，Worker 用 Consumer Group 領取。兩個 group 各拿一份完整訊息；同一個 group 開多個 Worker 就自動分攤。

    處理完才 XACK

    Worker 當掉時訊息留在待處理清單，別的 Worker 用 XAUTOCLAIM 接手閒置 60 秒的訊息

    At-least-once

    同一筆可能被處理兩次，所以每個判斷都要冪等：里程依時間戳去重

    只通知一次

    「判斷＋改旗標」寫在同一段 Lua，兩個 Worker 同時判斷也只警示一次

    db.py
    -- KEYS: arrived:{wp}  active  allin:{wp}
if redis.call('SADD', KEYS[1], uid) == 0 then return 0 end  -- 已經到過
local left = redis.call('SDIFF', KEYS[2], KEYS[1])          -- 還沒到的人
if #left == 0 and redis.call('SET', KEYS[3], 1, 'NX') then
  return 2                                              -- 全員到齊（只有一個 Worker 拿得到）
end
return 1                                                -- 抵達
    BEGIN;
INSERT INTO arrivals(wp_id, uid) VALUES (:wp, :uid) ON CONFLICT DO NOTHING;
SELECT COUNT(*) FROM active a
 WHERE a.trip_id = :t AND NOT EXISTS (SELECT 1 FROM arrivals r WHERE r.wp_id = :wp AND r.uid = a.uid)
 FOR UPDATE;                         -- 不鎖的話兩個 Worker 都會以為自己是最後一個
UPDATE waypoints SET all_in = TRUE WHERE id = :wp AND all_in = FALSE;  -- 看影響列數
COMMIT;
    Redis 單執行緒執行 Lua，中間不會插進別的指令，等於免費的「可序列化」隔離。

    落隊怎麼算：有路線時用「沿路線里程」的中位數當全隊中心。山路髮夾彎直線距離只差 400 m，沿路線可能已經落後 3 km，用直線距離會漏掉。

    09 · 失聯

    「沒有發生的事」怎麼偵測？讓 key 自己過期

    每筆回報重設一次心跳：移動中 90 秒、停著 10 分鐘。時間到 Redis 自動刪掉 key，並發出 Keyspace Notification，API 收到就發失聯警示。

    ingest.py、live.py
    # redis-server --notify-keyspace-events Ex
SET hb:57:25 1795423900000 EX 90       # 每筆回報重設
PSUBSCRIBE __keyevent@*__:expired
→ "hb:57:25"   ← 90 秒沒回報，key 過期的那一刻收到
    UPDATE rider_state SET last_seen = NOW() WHERE trip_id = 57 AND uid = 25;
-- 排程每 10 秒掃一次全表
SELECT uid FROM rider_state
 WHERE status = 'ok' AND last_seen < NOW() - INTERVAL '90 seconds';
UPDATE rider_state SET status = 'lost' WHERE …;
    SQL 要排程一直掃，掃的頻率決定延遲；Redis 是事件驅動，過期當下就通知，沒有人失聯時完全不花資源。

    10 · 規劃路線

    RediSearch 中文搜尋、RedisJSON 存路線

    15.6 萬筆地名與 POI 用 RediSearch 建中文全文＋地理索引，打字就自動完成；算好的路線（幾千個座標）存成 JSON，只取需要的部分。

    poi.py、routes.py
    FT.CREATE idx:poi ON HASH PREFIX 1 poi: LANGUAGE chinese
  SCHEMA name_n TEXT WEIGHT 2  kind TAG  rank NUMERIC SORTABLE  loc GEO
FT.SUGGET sug:poi "清" FUZZY MAX 8             → 清境農場、清水斷崖…
FT.SEARCH idx:poi "@kind:{fuel} @loc:[121.28 24.18 3 km]"
JSON.SET route:33 $ '{"coords":[…3,875 點],"steps":[…],"summary":{…}}'
JSON.GET route:33 $.summary                    → 只拿摘要，不搬幾千個座標
TS.MRANGE - + FILTER uid=1 GROUPBY cat REDUCE sum  → 你在各種路的平均速度
    -- LIKE '%清%' 用不到索引；中文要 ngram 全文索引
SELECT * FROM poi WHERE MATCH(name) AGAINST('清境' IN BOOLEAN MODE);
-- 自動完成要另外建前綴表或用 Elasticsearch
-- 路線存 JSON 欄位，取摘要要整欄讀出再解析（或 JSON_EXTRACT）
SELECT JSON_EXTRACT(route, '$.summary') FROM routes WHERE id = 33;
    一個查詢同時用全文、標籤、數值範圍、地理四種條件，Hash 寫進去就自動進索引。沿路線找加油站是一個 Pipeline 送出上百個 GEOSEARCH。

    路線本身用本機的 Valhalla（OpenStreetMap 台灣路網）計算：機車不上國道與快速道路、重機可以走快速道路（國道 3 甲例外），估時用你自己過去在各種路的實際速度。

    11 · 回放

    Stream 的 ID 就是時間索引

    軌跡、事件、聊天都存成 Stream，ID 是毫秒時間戳，XRANGE 依時間範圍取就好；速度、海拔放 TimeSeries，一個指令取全隊並降採樣。

    replay.py
    XRANGE track:48:9 1794906180000 1794919320000     # 一個人的整段軌跡
XRANGE trip:48:events - +                        # 事件時間軸
TS.MRANGE - + FILTER trip=48 kind=speed
  AGGREGATION avg 30000                          # 全隊速度，每 30 秒平均一點
XRANGE trip:48:routes - +                        # 騎到一半改過路線：哪段時間走哪條
    SELECT ts, lat, lon FROM track_points
 WHERE trip_id = 48 AND uid = 9 ORDER BY ts;     -- 要 (trip_id, uid, ts) 複合索引
-- 降採樣：每 30 秒一組
SELECT uid, FLOOR(ts / 30000) AS b, AVG(speed)
FROM track_points WHERE trip_id = 48 GROUP BY uid, b ORDER BY uid, b;
    同樣做得到，但 Redis 的資料一寫進去就是「依時間排好」的結構，不用另外建索引、也不用 GROUP BY。

    13 · 匯入舊紀錄

    舊資料加不進 Stream？整份重建，再原子換上

    支援靈感足跡的 GPX、Google 地圖時間軸、KML。問題是 Stream 的 ID 必須遞增，比現有最後一筆舊的點根本加不進去。

    1. 上傳：SET import:lock:{uid} NX 一人一次；原始檔暫存（1 小時 TTL）；XADD stream:import
    2. Worker（group import）把舊足跡＋新點依時間合併，同一秒已有點就算重複
    3. 在暫存 key 重建足跡、迷霧格子、每日里程、熱力圖、點亮鄉鎮
    4. WATCH 足跡 → MULTI → 一連串 RENAME → EXEC，一次換上
    importer.py
    WATCH footprint:1
XREVRANGE footprint:1 + - COUNT 1      # 跟讀取時的最後一筆一樣嗎？
MULTI
  RENAME imp:a1b2:footprint:1 footprint:1
  RENAME imp:a1b2:heat:1      heat:1
  RENAME imp:a1b2:fog:1:all   fog:1:all   # …一千多個 key
  INCR fp:ver:1                         # 查詢快取帶版本號，自然失效
EXEC                                   → nil：期間有新的 GPS 點寫入，重新合併
    BEGIN;
CREATE TABLE footprint_new AS SELECT … UNION SELECT …;   -- 合併
LOCK TABLE footprint IN ACCESS EXCLUSIVE MODE;          -- 換的時候鎖住，讀的人要等
ALTER TABLE footprint RENAME TO footprint_old;
ALTER TABLE footprint_new RENAME TO footprint;
COMMIT;
    跟 SQL「建新表、交易裡 RENAME」是同一招。讀的人不會看到一半舊一半新；騎車中匯入，剛回報的點也不會被蓋掉。實測 30 萬點（24 MB）約 9 秒。

    14 · 交易與一致性

    用 ACID 檢查 Redis

    Redis 的交易跟 SQL 不一樣：沒有 rollback，但單執行緒讓隔離性變簡單。

    Redis 的情況騎跡怎麼用
    原子性 AMULTI/EXEC 一起執行；Lua 整段原子；沒有 rollback（中間一個指令錯了，其他照樣執行）踢人一次移出成員、GEO、心跳；結束紀錄「移出＋是否最後一人＋改狀態」用 Lua
    一致性 C沒有外鍵、CHECK、NOT NULL，要由程式保證規則集中在 Lua 與 db.py；CI 冒煙測試走完整流程
    隔離性 I單執行緒，指令一個一個執行，天生可序列化；WATCH 樂觀鎖開始行程 WATCH 後檢查狀態，被搶先就重試
    持久性 D看設定：AOF everysec 最多掉 1 秒GPS 掉 1 秒可以接受；帳號一樣受 AOF 保護

    At-least-once 與冪等

    Worker 處理完才 XACK，當掉會被別人接手，所以同一筆可能處理兩次。統計的 Lua 記住「處理過的最後時間戳」，比它舊的直接略過；推播用 SET push:sent:{事件}:{收件人} NX 去重。重送不會重算里程、也不會推兩次。

    16 · 誠實面對

    Redis 不擅長、SQL 會比較好的地方

    情況原因如果要改進
    臨時報表（每月所有人騎幾公里）沒有 JOIN、GROUP BY，要事先設計好 key結束的行程歸檔到 PostgreSQL 做分析
    資料一大成本就高全部在記憶體舊軌跡壓縮或搬到磁碟資料庫
    約束要自己寫沒有外鍵、CHECK規則集中在 db.py＋Lua，CI 測試
    刪一個行程要刪很多 key子資料分散在 trip:{tid}:*SCAN MATCH 逐批找出來刪
    結論：騎跡的資料大多是「高頻寫入、即時、會過期、要地理和時間查詢」，正好是 Redis 的強項；長期分析才適合 SQL。實務上常見兩者並用：Redis 處理即時，SQL 存歸檔做分析。

    17 · 戰情室與後台

    給在家、在支援車上的人看

    戰情室跟行程頁訂閱同一個 Pub/Sub 頻道；觀看連結免登入（SET watch:{tok} 57 EX，行程結束就失效）。

    • 沿途天氣：位置先在本機用 GEOSHAPE 換成鄉鎮，只向氣象署要整個縣市的預報，座標不會送出去；cache-aside 30 分鐘
    • 前方路況：交通部 TDX 每月只有 4,500 次，SET lock:tdx NX EX 30 只讓一個 Worker 去抓（防 cache stampede），重建時寫暫存 key 再 RENAME
    • 管理後台：每秒寫入、Pub/Sub 訊息量、推播數都是 TimeSeries；SCAN＋TYPE／TTL 看 key 型別分布；Worker 的 lag 用 XINFO GROUPS

    心得

    • 資料模型比程式重要。一開始想清楚「怎麼查」，型別選對了，程式就很短；選錯（例如足跡用 Stream 卻要補舊資料）就要重建。
    • 原子性要放在資料庫裡。「只通知一次」「全員到齊」這種判斷寫在 Python 裡一定會有競爭條件，搬進 Lua 就沒了。
    • 「沒發生的事」最難偵測。失聯靠 TTL 過期事件，比排程掃表乾淨很多。
    • 跟 AI 合作要有驗收機制。CI、截圖、實機測試、交接紀錄，缺一個就會有「說好了其實沒好」。

    尚待解決

    • 手機網頁鎖螢幕就不能定位，背景回報目前靠 Traccar；之後包成 App（Capacitor＋背景定位）
    • 結束的行程歸檔到 SQL 做長期分析
    • 全站省電：靜止時地圖不重畫；出發前下載沿線地圖，山區沒訊號也能用
